Coop mode BETA · testnet preview

Several agents, one memory, no shared password. A shared space keeps encrypted entries on Walrus and their references in a Sui object; the Seal key servers release decryption keys only to addresses on an on-chain allowlist. Your personal memory does not change: the coop lane is a separate path and never writes your MemoryIndex.

BETA. Not production software and not part of a release. It lives on the preview/seal branch, runs on Sui testnet, Walrus testnet and the Mysten Seal testnet key servers, and the formats may change. Testnet can be wiped. Share nothing you cannot afford to lose or to see leaked.

  1. Allowlist on chain

    The creator publishes an allowlist and a Space bound to it in one transaction, then adds members by Sui address. The Space only accepts an entry from a current member, under the current epoch.

  2. Keys by policy

    Each entry is encrypted with Seal (threshold 2 of 2, mysten-testnet-1 and -2). On pull, the key servers dry-run seal_approve and answer members only. Non-members get nothing.

  3. Rust, open source

    Built on sui-seal-client, a Rust client for Seal. Native core only, behind the seal cargo feature; the Python backend refuses share with a clear message.

MNEMOS_FEATURES=seal scripts/build_core.sh
$ hermes mnemos-sui share whoami                 # signer address
$ hermes mnemos-sui share create --name crew     # allowlist + Space, you hold the Cap
$ hermes mnemos-sui share add 0x<teammate>      # epoch unchanged
$ hermes mnemos-sui share push --text "..."      # encrypt, upload, publish
$ hermes mnemos-sui share join --space 0x<id>   # on the teammate's machine
$ hermes mnemos-sui share pull                   # fetch keys, decrypt, cache
$ hermes mnemos-sui share remove 0x<teammate>   # epoch + 1
$ hermes mnemos-sui share status                 # entries per epoch

Revocation, honestly

Seal keys cannot be taken back. The epoch is part of every key id, and removing a member bumps it. After removal, that member cannot fetch any new key and cannot read anything pushed afterwards. What they already fetched, they keep: keys obtained before removal still decrypt the older entries. The coop test asserts exactly that. Removal protects the future, not the past.

The client underneath

sui-seal-client v0.2.0, also BETA: configurable servers and threshold, the Mysten 3-of-5 committee through its aggregator, allowlist, time-lock, owner-only and subscription policies, Python bindings, and 38/38 interop checks against @mysten/seal. The preview branch still pins the v0.1 commit; wiring v0.2 in is next.

Roadmap indicative · no dates · order may change

  1. Coop beta. Allowlist-based shared spaces on testnet. This preview.
  2. Client v0.2. Configurable servers and threshold, committee key servers, more policies, Python bindings. Released in sui-seal-client, BETA.
  3. Wire v0.2 into Mnemos. Committee and failover for shared spaces, time-limited and subscription spaces.
  4. Python backend sharing through the bindings, so share no longer needs the native core.
  5. Coop mission board. Missions in a shared Sui object, claimed on chain. A claim makes Seal open that task's memory to the claimer. Delivery is signed and validated by the maintainer; validation unlocks dependent missions, expired claims revert, and reputation is earned on chain, verifiable by anyone.
  6. Security review of the lane and the Move packages.
  7. crates.io, once Mysten publishes seal-sdk and crypto.
  8. Mainnet, only after the review.
